# Svc::DpCatalog Component

## 1 Introduction

`DpCatalog` is an active F´ component that manages the downlink of generate data products. The data products were previously generated by components into a project-specific set of directories. Upon command, `DpCatalog` will build a catalog of existing data products and start downloading them. They are downloaded in order of priority, then generation time. The priority is the one stored in the file unless it was changed with `SET_DP_PRIORITY`, which reprioritizes a single product and, if a state file is configured, records the new priority in it so that the change is kept across catalog rebuilds and restarts.

NOTE: This release has an early prototype that will do the following:

1. Reads the data product files from the specified directory.
2. Puts them in priority sorted list.
3. Sends requests to `Svc/FileDownlink` to downlink each file in the list.
4. Stop transmissions in progress
5. Allow insertion of new products after the catalog is built
6. Clear the catalog via command
7. Restrict a transmission to an inclusive priority range (`START_XMIT_CATALOG_WITH_PRIORITY`)
8. Change the transmit priority of one product by command (`SET_DP_PRIORITY`); the change is kept in the state file, if one is configured
9. Delete one product by command (`DELETE_DP`): its file, its catalog entry and its state file record
10. Reschedule one transmitted product for downlink by command (`RETRANSMIT_DP`), for a product corrupted in transit or lost on the ground

It does not:

1. Send data product files in pieces. It only sends whole files, so if the downlink is interrupted, the whole file will have to be retransmitted.

Features and more extended unit testing will be added over time. Use at your own risk!

## 3 Design

### 3.1 Assumptions

The design of `DpCatalog` assumes the following:

1. A file system exists to store the data product files.
2. The contents of the data product files match the data product specification.
3. The file downlink will acknowledge completion of each file

#### Sequence of Commands

When the software is first started, the catalog data structure is empty. The catalog must be built before starting downlink. The `BUILD_CATALOG` command was implemented separately from the `START_XMIT_CATALOG` command to start downlinking so the software could build the catalog prior to a communication session and execute the downlink during communication. Downlink can be halted by issuing the `STOP_XMIT_COMMAND` in the middle of the downlink. If for some reason the state in the state file, the contents of the tree and the data products get out of sync, a `CLEAR_CATALOG` command can be issued. Then the `BUILD_CATALOG` command can be invoked to rebuild the state based on the existing set of data product files only. This will caused downlinked state to be lost, so data products not deleted after downlink would be readded to the pending list of downlinks. `DELETE_DP` likewise needs a built catalog (or the state file data loaded by the last build); a transmitted product deleted with it is not readded by a later `CLEAR_CATALOG`/`BUILD_CATALOG` (3.6.9). `SET_DP_PRIORITY` can be issued once the catalog is built, before or during a `START_XMIT_CATALOG`, to change the order of products not yet sent; if a state file is configured the change is recorded in it and kept across `BUILD_CATALOG`, `CLEAR_CATALOG`, and restart (3.6.8). `RETRANSMIT_DP` also needs a built catalog (it is rejected `NOT_BUILT` before `BUILD_CATALOG` and after `CLEAR_CATALOG`) and, like `SET_DP_PRIORITY`, is accepted during a transmission (3.6.10).

### 3.6 Algorithms

#### 3.6.1 Data Product Sorting

Overall priority is determined by comparing two entries' priority, timestamp, id, and directory index in that order with lower numerical values holding higher priority (see `DpCatalog::DpStateEntry::compareEntries`). The following logic is implemented:

1. Data Product Priority - Data products are generated with a priority, where the lower the number the higher the priority.
2. Data Product Generation Time - If priorities are the same, the older data is prioritized over the newer.
3. Data Product ID - If priorities and time are the same (highly unlikely), then lower IDs are prioritized first.
4. Directory Index - If a file of the same name (same priority, time, and id) is held in two configured directories, the lower index in the configured directory list is prioritized first. The directory is part of the key so that two distinct files never share a catalog entry, whatever priorities they hold or are set to (3.6.8).

#### 3.6.2 Reading Files

The `configure()` function is provided an array of directories where data product files are generated by `Svc/DpWriter`. When the `BUILD_CATALOG` command is executed, the headers of the data product files are read and the metadata in their headers is processed and stored as a data structure for sorting. The file name is not stored to conserve memory.

#### 3.6.3 Sorting Algorithm

The data products are sorted using a `Fw::RedBlackTreeSet` (a self-balancing binary search tree). Entries are ordered by the priority comparison described above, so the highest priority entry is always first in the set.

#### 3.6.4 Tree Traversal for Downlink

When data products are downlinked, entries are retrieved in priority order by iterating the set from `begin()`, which always yields the highest priority (lowest value) entry. The walk skips, without removing, entries whose priority value is below the `startPriority` of the active transmit command and stops at the first entry above its `endPriority`, since nothing after it can be in range; the first entry inside the range is the next file to send. As each file completes downlink, its entry is removed from the set, so the next walk again starts at `begin()`. Entries inserted while a downlink is in progress (e.g. via `addToCat`) are placed in priority order and picked up by subsequent walks if they fall inside the range. The walk is bounded by the catalog size (`DP_MAX_FILES`); skipped out-of-range entries are revisited on every `sendNextEntry`, which is acceptable at that bound. Entries left outside the range remain pending (and counted in `m_pendingFiles`) for a later transmit command with a range that covers them. Consequently `CatalogXmitCompleted` means that the requested range is exhausted, not that the catalog is empty: products outside the range may still be pending. A range that matches no pending product is accepted and reports `CatalogXmitRangeStarted` immediately followed by `CatalogXmitCompleted` with 0 bytes, exactly as an empty catalog does, unless a send left in flight by `STOP_XMIT_CATALOG` is pending: `CatalogXmitCompleted` then follows that file's completion and reports its bytes. The file in flight is never preempted: when its `fileDone` arrives the next send is the highest priority in-range entry remaining in the set, whether it was there at `BUILD_CATALOG` or was inserted since.

#### 3.6.5 State File

When a data product is downlinked, it is marked in the node as completed, but the state is also written to a file so that downlinked state is preserved across restarts of the software. When the catalog is built, the state file is first read into a data structure in memory. A record's directory index is stored as read, without checking it against the configured directory list; `DELETE_DP` checks it before use (3.6.9).
Entries whose state-file record is `TRANSMITTED` are skipped during catalog build, emit a `DpFileSkipped` event, and are not counted as pending.

#### 3.6.6 FileDone Handling

Every `sendFile` call returns a `SendFileResponse` whose `context` FileDownlink assigns to that send and echoes back in `fileDone`. `DpCatalog` keeps the context of the send in flight and applies a `fileDone` only while a send is in flight and the context matches. Anything else is a late callback from a send abandoned by `BUILD_CATALOG` or `CLEAR_CATALOG` (`STOP_XMIT_CATALOG` alone keeps the send in flight, so its completion is still recorded, and a `START_XMIT_CATALOG` issued before it arrives starts no new send until then, so the file is not sent twice): it is reported with `StaleFileDone` (`WARNING_LO`, id 50, an expected consequence of an operator command rather than a fault) and the transmit in flight, if any, is left untouched. `CLEAR_CATALOG` issued mid-transmit closes the transmit session itself, as `STOP_XMIT_CATALOG` does: a waited `START_XMIT_CATALOG` is answered with `EXECUTION_ERROR` at that point, so a later `BUILD_CATALOG` or `START_XMIT_CATALOG` is not refused as in progress and the late callback is only reported. This replaces the `FW_ASSERT` that made a late `fileDone` FATAL (#5777). The discrimination requires the provider to assign a distinct `context` to every send, as `Svc/FileDownlink` does; a provider that echoes a constant context (for example `Svc/Ccsds/CfdpManager`, which returns the port number) cannot distinguish a late callback from the current send and is not supported on this port. Note: `FileComplete` must not be shared with other `SendFile` clients on the same FileDownlink; foreign completions would be reported as `StaleFileDone`.

#### 3.6.7 Runtime Insertion (`addToCat`)

`Svc/DpWriter` reports every data product file it writes on its `dpWrittenOut` port (file name, priority, size); the `DataProducts` subtopology connects it to `addToCat`. The handler reads the header of the named file and inserts an entry exactly as `BUILD_CATALOG` does (`processFile`), so a product added at runtime sorts identically to one found by a build. The priority and size carried by the port are not used: the header is the authoritative source and is read anyway for the id and time tag, which the port does not carry. The cases are handled as follows:

| Condition | Behavior |
|---|---|
| Component not configured (`ComponentNotInitialized`) or configured with no slots (`ComponentNoMemory`) | The file is not recorded; the corresponding warning is emitted, as for the commands. |
| Catalog not built (no `BUILD_CATALOG` yet, or `CLEAR_CATALOG` since the last build) | The file is not recorded; `NotLoaded` is emitted. The file is on disk in a managed directory and is found by the next `BUILD_CATALOG`. |
| File is not under a configured directory | `DirectoryNotManaged`; the file is ignored. |
| File cannot be read or has a bad size, header, CRC, or name | The same `FileSizeError`/`FileOpenError`/`FileReadError`/`FileHdrError`/`FileHdrDesError`/`FileNameFormatError`/`InvalidFileName` events as at build time; nothing is inserted. |
| Tree insert fails although a slot is free (not expected) | `DpInsertError`; nothing is inserted. |
| Product already in the catalog (same directory, `id`, `tSec`, `tSub`; the priority is not compared, since `SET_DP_PRIORITY` may have changed it) | `DpDuplicate`; pending counters are unchanged. `DpDuplicate` is `DIAGNOSTIC`, which `Svc/EventManager` filters out by default (`FILTER_DIAGNOSTIC_DEFAULT`), so it is not downlinked unless that filter is enabled. |
| Product recorded as `TRANSMITTED` in the state file data (loaded by the last `BUILD_CATALOG` and updated by each completion since, 3.6.8) | The file is not recorded; `DpFileSkipped` is emitted, as at build time. Records appended since that build (3.6.6) are applied at the next `BUILD_CATALOG` as long as the product has, or can get, a slot in the state file data: the file may hold several records for one product (3.6.8) and `loadStateFile` reads them all, but a record for a product beyond the configured number of distinct products (at most `DP_MAX_FILES`) is skipped without an event, so such a transmitted product is re-added and re-sent by the rebuild. Delete downlinked products with `DELETE_DP` (3.6.9), which drops the state file record and frees the slot, so the number of distinct products in the state file stays within the slot budget; a file removed outside the component keeps its record until the next `BUILD_CATALOG` prunes it. `RETRANSMIT_DP` (3.6.10) resets such a record so that the product is sent again. `DpWriter` reports each file once, so the runtime skip only arises if an identical product is rewritten. |
| Catalog has no free slot (`DP_MAX_FILES`/configured slots in use) | `DpCatalogFull`; nothing is inserted. The product is not inserted when a slot later frees: the entry being downlinked holds its slot until its `fileDone`, so at most slots − 1 products can be inserted during a transmission. The file remains on disk and is found by the next `BUILD_CATALOG`, which a transmission in progress refuses. `DpCatalogFull` is throttled after 10 occurrences, after which refused products are not reported. |
| Otherwise | The entry is inserted in priority order, `DpFileAdded` is emitted, and the pending file/byte counts are updated. |

After a successful insert: if a transmission is in progress, the entry is picked up as described in 3.6.4. Otherwise, if the most recent transmit command (`START_XMIT_CATALOG` or `START_XMIT_CATALOG_WITH_PRIORITY`) had `remainActive` set and a pending entry lies inside its priority range, the transmission is (re)started immediately and the highest priority in-range entry is sent; this holds whether that transmission completed or was halted by `STOP_XMIT_CATALOG`, because `remainActive` and the range are replaced only by the next transmit command, so a runtime insert resumes a stopped transmission. A transmission restarted this way keeps the byte tally of the session it continues: the tally is zeroed only by a transmit command, so the `CatalogXmitCompleted` emitted when the restarted transmission drains reports the bytes of the previous session plus the newly inserted product(s). Otherwise the entry waits for the next transmit command. The state file is not rewritten on insert: a newly written product has no transmit state to record, and its `TRANSMITTED` record is appended when its downlink completes, as for any other entry.

#### 3.6.8 Reprioritization

`SET_DP_PRIORITY` changes the transmit priority of one catalog entry (SVC-DPCAT-017). The priority is the first field of the sort key (3.6.1), so the entry cannot be modified in place: the handler looks the entry up by its identity fields (`id`, `tSec`, `tSub`) with a linear walk of the set (`findProductEntry`, bounded by `DP_MAX_FILES`), removes it, sets the new priority, and re-inserts it. Only that entry moves and the set is only touched from the component's own thread, so a transmission in progress is not corrupted: each send restarts the walk at `begin()` (3.6.4), so the next send honors the new order. If the reprioritized entry is the one in flight, the send itself is unaffected: `fileDone` locates the entry to remove by identity, not by the sort key of the copy it keeps (`m_currentXmitEntry`, which is updated too so that the record written on completion carries the current priority).

A `START_XMIT_CATALOG_WITH_PRIORITY` range is checked against the priority each entry has when it is reached, so a product moved into or out of the active range by `SET_DP_PRIORITY` is sent, or left pending, accordingly.

The change is made by `setDpPriority`, which a future port could call as the command handler does. It updates the product's record in the state file data (`updateStateFileData`), which holds one `DpRecord` per product, or adds one with the product's current state. If a state file is configured, the new priority is then recorded in it (SVC-DPCAT-021) by rewriting the file from the state file data; `DpRecord` already carries a priority field, so the file format is unchanged. Unlike the data in memory, the file on disk may hold more than one record for a product: the rewrite after a priority change, then the record appended on completion (3.6.6); the last one read wins. On the next `BUILD_CATALOG`, records are matched to files by directory and identity (`id`, `tSec`, `tSub`) rather than by the full record, and a matched record supplies the priority as well as the transmit state, so the product keeps its new priority, and once sent is skipped as transmitted. Completion also updates the state file data, so a later rewrite (another priority change or the next `BUILD_CATALOG`) keeps it. The data product file header is not rewritten. A runtime `addToCat` of a file already in the catalog is recognized as a duplicate after a priority change, with or without a state file and whether or not the change could be recorded, because the duplicate check compares the product identity (directory, `id`, `tSec`, `tSub`) rather than the sort key (3.6.7). A slot of the state file data is consumed by each product loaded from the state file at build, and by each product first recorded by a completion or a priority change since; a slot not visited by the last build belongs to a file that is gone and is reused. If no slot is free, `StateFileFull` (`WARNING_HI`, id 55) is reported when a state file is configured: on `SET_DP_PRIORITY` the new order still applies until the next rebuild and the command fails; on completion the product is still appended to the state file. A rewrite that fails part-way leaves the records written before the failure in the file; the next successful rewrite replaces them. Without a state file the change applies to the catalog in memory only and the command succeeds. To return to the file priority, set it again. The lookup is by identity without the directory, so if two configured directories hold a file of the same name (same `id`, `tSec`, `tSub`), the command moves the first entry found in sort order. The directory index is the last field of the sort key (3.6.1), so the two entries never share a key: moving one onto the other's priority keeps both in the catalog, both are transmitted (lower directory index first), and the pending counters stay exact (DpWriter writes each product once, to one directory, so the case does not occur with the standard producer).

#### 3.6.9 Deleting a Data Product

`DELETE_DP` deletes one data product (SVC-DPCAT-023), named by `id`, `tSec` and `tSub` as `SET_DP_PRIORITY` names it. A pending product is found in the catalog (`findProductEntry`); a transmitted product has no catalog entry and is found by its record in the state file data (`findStateFileSlotByIdentity`), which `BUILD_CATALOG` loads from the state file and every completion or priority change keeps current (3.6.8). Both lookups are linear walks bounded by `DP_MAX_FILES`. The cases are handled as follows:

| Condition | Behavior |
|---|---|
| Component not configured (`ComponentNotInitialized`) or configured with no slots (`ComponentNoMemory`) | Nothing is deleted; the corresponding warning is emitted, as for the other commands. |
| Product is the one being transmitted (`m_currentXmitEntry`), including a send left in flight by `STOP_XMIT_CATALOG` | Nothing is deleted; `DpInFlight` (`WARNING_HI`, id 58) is emitted and the command fails with `EXECUTION_ERROR` (SVC-DPCAT-024). The product can be deleted once its `fileDone` arrives and its completion is recorded. |
| Product is neither in the catalog nor in the state file data (including before `BUILD_CATALOG`, after `CLEAR_CATALOG`, already deleted, or a transmitted product whose completion was reported with `StateFileFull`, 3.6.8: rebuild the catalog, which re-adds it as pending, then delete it) | Nothing is deleted; `DpNotFound` is emitted, as for `SET_DP_PRIORITY`, and the command fails with `EXECUTION_ERROR`. |
| Record found in the state file data names a directory that is no longer configured (the directory list changed across a restart, or the file is corrupt; records are loaded without a range check on the directory index, 3.6.5) | Nothing is deleted; `DpNotFound` is emitted and the command fails with `EXECUTION_ERROR`. |
| File name cannot be formatted (not expected) | `FileNameFormatError`; nothing is deleted and the command fails with `EXECUTION_ERROR`. |
| File cannot be removed (`Os::FileSystem::removeFile` fails other than `DOESNT_EXIST`) | `DpFileRemoveError` (`WARNING_HI`, id 59) with the status; the catalog and state file are left as they were, describing what is still on disk, and the command fails with `EXECUTION_ERROR`. |
| Otherwise | The file is removed first (a file already gone is a stale reference and is treated as removed), then the catalog entry, with the pending file and byte counts, and the state file data slot (the last slot moves into it). `DpDeleted` (`ACTIVITY_HI`, id 57) reports the file and the transmit state the product had. If the product had a state file record and a state file is configured, the file is rewritten without it (`pruneAndWriteStateFile`), so that a rebuild or restart does not treat a product rewritten with the same identity as transmitted; a rewrite failure is reported by `StateFileOpenError`/`StateFileWriteError` and the command fails with `EXECUTION_ERROR` although the product is gone from disk and memory. |

The file is removed before the data structures are changed so that a failure leaves the catalog describing what is on disk. A delete during a transmission of another product is safe: only the component's thread touches the catalog, and each send restarts the walk at `begin()` (3.6.4), so a deleted pending product is simply never sent and `CatalogXmitCompleted` reports the bytes actually sent. The lookup is by identity without the directory, so if two configured directories hold a file of the same name the command deletes the first entry found in sort order (lowest directory index), as `SET_DP_PRIORITY` moves the first; a second `DELETE_DP` deletes the other. While one of them is being transmitted, `DELETE_DP` of that identity is refused with `DpInFlight` for both, since the in-flight check compares the identity only; delete the other after the send completes. Without a state file the delete applies to the file and the catalog in memory only. Deleting the product named by a `START_XMIT_CATALOG` range leaves the range unchanged. Deletes issued in bulk by a ground tool are queued on the component's command queue like any other command: issue them from a sequence, or wait for each command response, so that a burst never exceeds the configured queue depth (10 in `Svc/Subtopologies/DataProducts`).

#### 3.6.10 Retransmission (`RETRANSMIT_DP`)

A product that has completed downlink is removed from the catalog (3.6.4) and recorded `TRANSMITTED` in the state file data and the state file (3.6.6), so every later `BUILD_CATALOG` skips it; the only way to send it again was to delete the state file on the file system and rebuild, which resends everything. `RETRANSMIT_DP` resends one product (SVC-DPCAT-025), named by `id`, `tSec` and `tSub` as `SET_DP_PRIORITY` and `DELETE_DP` name it. A transmitted product has no catalog entry, and may have no state file record either (no state file configured, or its completion reported `StateFileFull`, 3.6.8), so the command locates its file by the canonical name `Dp_<id>_<tSec>_<tSub>.fdp` under each managed directory, in configuration order, and uses the first file that exists; the other commands likewise act on the first match (3.6.9). The product is then cataloged again by `processFile`, exactly as `BUILD_CATALOG` and `addToCat` do. `processFile` applies the product's state file record (`getFileState`): a record reading `TRANSMITTED` would make it skip the file, and a recorded priority would replace the header priority. The record found for the file's directory and identity (`findStateFileSlot`) is therefore dropped first (the last slot moves into its place, as `DELETE_DP` does), so the product is cataloged from its header alone and rescheduled at the header priority: a priority set by `SET_DP_PRIORITY` before the first downlink does not carry over to a retransmission; the operator sets it again if wanted. The product is then recorded `UNTRANSMITTED` at the header priority in the state file data (`updateStateFileData`, as a completion records it: a product that had a record always gets one, since its slot was just freed, while a product without one may find the data full, `StateFileFull`, 3.6.8), and the state file is rewritten from the state file data (`pruneAndWriteStateFile`, as the other commands do), so that a `BUILD_CATALOG` after a restart catalogs the product rather than skipping it. The rewrite also drops a `TRANSMITTED` record that was appended without a slot (`StateFileFull`, 3.6.8), so that the stale state cannot return on a later build that has a free slot for it. The cases are handled as follows:

| Condition | Behavior |
|---|---|
| Component not configured (`ComponentNotInitialized`) or configured with no slots (`ComponentNoMemory`) | Nothing is rescheduled; the corresponding warning is emitted by `checkInit` and the command fails with `EXECUTION_ERROR`, without a `DpRetransmitError`, as for the other commands. |
| Catalog not built (no `BUILD_CATALOG` yet, or `CLEAR_CATALOG` since the last build) | `DpRetransmitError` (`WARNING_HI`, id 60) with `NOT_BUILT`; `EXECUTION_ERROR`. The state file data of the last build is needed to recognize the product's record. |
| Product is the one being transmitted (`m_currentXmitEntry`), including a send left in flight by `STOP_XMIT_CATALOG` | `DpRetransmitError` with `IN_FLIGHT`; `EXECUTION_ERROR`. The send in progress completes and is recorded normally; retransmit after its `ProductComplete`. |
| Product is pending in the catalog (`findProductEntry`) | `DpRetransmitError` with `PENDING`; `EXECUTION_ERROR`. The product has not been transmitted and will be sent by the transmission in progress or the next transmit command; nothing is changed. |
| No file `Dp_<id>_<tSec>_<tSub>.fdp` exists in any managed directory | `DpRetransmitError` with `NOT_FOUND`; `EXECUTION_ERROR`. A product deleted after downlink cannot be resent. |
| The file name cannot be formatted under a managed directory (not expected) | `DpRetransmitNameError` (`WARNING_LO`, id 62) names the directory and the format status; the directory is skipped and the search goes on with the next one, so a file in a shorter directory is still found, and the product is reported `NOT_FOUND` if no directory holds it. |
| The file cannot be cataloged: bad size, header, CRC or name, header already `TRANSMITTED`, tree insert failure, or no free slot | The same event as at build time (`FileSizeError`/`FileOpenError`/`FileReadError`/`FileHdrError`/`FileHdrDesError`/`FileNameFormatError`/`InvalidFileName`/`DpFileSkipped`/`DpInsertError`/`DpCatalogFull`) followed by `DpRetransmitError` with `FILE_ERROR`; `EXECUTION_ERROR`. The record is put back as it was (slot, record and visited flag), so neither the state file data nor the state file is changed. |
| Otherwise | The product is inserted in priority order with `DpFileAdded`, the pending counts are updated, and `DpRetransmitScheduled` (`ACTIVITY_HI`, id 61) reports the file and the priority it is sent at. The product is recorded `UNTRANSMITTED` in the state file data (`StateFileFull` if no slot is free and a state file is configured: the product is then known by its file alone until its completion, as after a completion reported `StateFileFull`). If a state file is configured, the file is rewritten; a rewrite failure is reported by `StateFileOpenError`/`StateFileWriteError` and the command fails with `EXECUTION_ERROR` although the product is rescheduled in memory, as for `DELETE_DP`; only a `BUILD_CATALOG` (which reloads the file) before its downlink completes would skip it again. Otherwise `OK`. |

After a successful request the product is scheduled as a runtime insert is (3.6.7, SVC-DPCAT-027): a transmission in progress picks it up in priority order after the file in flight if its priority is inside the active range (3.6.4); otherwise, if the last transmit command had `remainActive` set and any pending product (the rescheduled one or one left behind) is inside its priority range, that transmission resumes immediately, sends the in-range products in priority order and continues the byte tally of that session; otherwise it waits for the next transmit command, as does a rescheduled product outside the active range. When its downlink completes, its record is updated `TRANSMITTED` in the state file data and appended to the state file (3.6.6), so the next build skips it again; the state file data holds one record per product, so the file does not grow with the number of retransmissions beyond the appended completions, which the next rebuild prunes to one record per product. The command is accepted during a transmission, unlike `BUILD_CATALOG`. The lookup is by identity without the directory, so if two configured directories hold a file of the same name the command reschedules the one in the first directory, in configuration order; while either is pending or in flight the identity is reported `PENDING` or `IN_FLIGHT`, since both checks compare the identity only. Retransmits issued in bulk by a ground tool are queued on the component's command queue like any other command, and each one rewrites the whole state file when one is configured: issue them from a sequence, or wait for each command response, so that a burst never exceeds the configured queue depth (10 in `Svc/Subtopologies/DataProducts`), which is shared with `fileDone` and `addToCat`. Note that while the last transmit command had `remainActive` set, a successful `RETRANSMIT_DP` starts the downlink at once and the resumed transmission sends every pending product in range, not only the rescheduled one; between passes this records them `TRANSMITTED` without a receiver. To stage retransmits for a later pass, make sure the last transmit command had `remainActive` false (`STOP_XMIT_CATALOG` does not clear it), or issue the retransmits once the pass is open.
